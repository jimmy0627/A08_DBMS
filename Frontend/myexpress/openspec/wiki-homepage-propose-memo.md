# 明日方舟 Wiki 主頁 HTML 備忘錄

此文件供下一步 `/opsx:propose` 使用，目標是把 `DESIGN.md` 轉成可執行的首頁 HTML 提案。

## 一句話目標
做出一個像「羅德島終端機」的 Wiki 主頁，讓使用者查資料時像在看機密檔案，而不是一般維基。

## 已確認的設計方向
- 深色底、青色強調、少量紅色警示。
- 0px 圓角、極細邊框、低陰影或無陰影。
- 中文主標題搭配小字英文副標，常見 `//` 與全大寫字樣。
- 資訊密度高，但要靠網格和區塊切分維持秩序。
- 整體氣氛偏冷靜、戰術、工業、終端機感。

## 主頁建議結構
1. 頂部導覽列
2. Hero / 首屏介紹區
3. 搜尋與快速入口
4. 分類卡片區
5. 熱門內容或最新更新區
6. 幹員 / 角色 / 資料入口區
7. 右側資訊欄或公告欄
8. 頁尾資訊區

## 首頁區塊與 API 對應

| 首頁區塊 | 是否需要 API | 建議 API | 用途 |
| --- | --- | --- | --- |
| 頂部導覽列 | 否 | 無 | 站名、分類錨點、快速跳轉，先用靜態連結即可。 |
| Hero / 首屏介紹區 | 部分需要 | `operators/list/`、`stages/` | 如果要顯示「資料庫總量 / 內容更新數 / 可查詢項目」這類統計，可先用這兩個 API 組出首頁摘要。 |
| 搜尋框 | 是 | `operators/list/`、`stages/`，之後可搭配 `operator/<op_id>/skills/`、`operator/<op_id>/modules/` | 先做關鍵字搜尋入口，查到結果後再跳轉到幹員或關卡詳情頁。 |
| 快速入口卡片 | 否 | 無 | 角色、關卡、活動、素材等分類入口多半是固定導覽，不需要先接 API。 |
| 重點條目 / Featured Files | 是 | `stages/<stage_id>/guides/` | 很適合顯示某關卡的攻略列表或推薦內容。 |
| 最新更新 / Recent Log | 部分需要 | 目前無直接對應 API | 若要真實更新紀錄，建議未來新增首頁聚合 API 或從攻略/關卡資料推導。 |
| 公告 / Notice | 部分需要 | 目前無直接對應 API | 若要做正式公告，建議另建公告資料表或首頁公告 API；現在可先手寫靜態內容。 |
| 幹員 / 角色 / 資料入口區 | 是 | `operators/list/`、`operator/<str:op_name>/materials/<int:elite_stage>/`、`operator/<int:op_id>/skills/`、`operator/<int:op_id>/modules/`、`operator/<int:op_id>/calculate-total/` | 這一塊是最適合接 API 的核心資料區，能從列表進入詳細養成資訊。 |
| 頁尾資訊區 | 否 | 無 | 版權、版本號、資料來源說明，多半是靜態文字。 |

## API 整合策略
- 這組 API 現在比較像「內容詳情層」，最適合接到首頁之後的二級頁面或搜尋結果頁。
- 首頁本身應優先接 `operators/list/` 和 `stages/` 這種列表型 API，因為它們可以提供首頁摘要、搜尋候選與快速入口。
- 像 Hero、最新更新、公告這些首頁模組，若要動態化，最好另外補一個「首頁聚合 API」，一次回傳首頁需要的精簡資料。
- `guides/create/`、`guides/<int:guide_id>/delete/`、`stages/create/`、`users/.../update/` 這類寫入 API，比較像管理功能，不適合直接放在首頁公開區。

## 前端接法提醒
- 前端現在在 `myexpress`，API 在 `Wiki_Database`，兩者不是同一個服務。
- 如果首頁要直接 `fetch` Django API，需要同源代理、反向代理，或是讓 Express 轉發 `/api/*` 到 Django。
- 不建議首頁直接硬寫所有資料路徑，先把首頁做成「入口面板」，再逐步把需要的卡片換成 API 資料。

## 可直接帶進 `/opsx:propose` 的語氣
- 這不是一般 wiki 主頁，而是「羅德島資料終端」風格首頁。
- 所有元件都要服務於「查資料像在操作機密系統」這個感受。
- 未定義部分以克制、方正、資料庫感為優先，不要偏可愛或商業促銷風。

## 可能的首頁重點
- 讓人一眼知道這是明日方舟 Wiki。
- 讓搜尋與分類入口優先可見。
- 讓內容看起來很有資料庫層級，而不是一般新聞站。
